# 后训练:SFT 试点(Task 7)

目标是在课程提供的 Qwen3.8-27B-AWQ-INT4 上训练一个 LoRA 适配器,让模型在**不给任何提示**的情况下选对知识库的品类名(issue #4 的上下文蒸馏),并确认适配器能被 vLLM 加载服务。这是流程试点,**不是质量结论**。

## 1. 文件

| 文件 | 作用 |
|---|---|
| `prepare_data.py` | 从评测运行的轨迹生成训练用的聊天 JSONL:只收开发用例,只保留评分器判为成功且没有被拒绝步骤的运行,检查保留集泄漏 |
| `lora_int4.py` | 在 INT4 检查点上加 LoRA(不用 peft),导出 vLLM 可服务的 peft 格式 |
| `sft.py` | 训练、保存、重载检查 |
| `../configs/sft.yaml` | 训练配置 |
| `../deploy/tacc/train-sft/` | TACC 训练作业(2 张 GPU,1 小时) |
| `../deploy/tacc/train-sft-serve/` | 把适配器和基座一起交给 vLLM 服务,比较第一步动作 |
| `results/` | 本次试点的日志、元数据和对比结果 |

适配器权重(约 218 MB)不放进 git,保存在集群上:`$TACC_USERDIR/adapters/sft-pilot-28670/`。

## 2. 训练数据

- **来源**:评测运行器在开发集上以温度 0.7 采集的轨迹(作业 28620),每个用例 6 次,配置 B3h,即给了品类列表提示。60 次运行里 19 次被评分器判为成功,共 69 个模型调用。
- **去掉提示**:记录下来的输入里**没有**品类列表,与部署形态的 harness 发送的完全一致。动作来自带提示的那次运行,所以学到的是"没有提示也选对品类"。
- **编码**:提示是服务端构造的生成提示(关闭思考),目标是动作文本加结束符,只对目标算损失。
- **实际用于训练的**:69 个里有 38 个超过 4096 token 被丢弃(显存限制:约 5K 到 10K token 的后续步骤放不进 24 GiB),剩下 31 个,其中 26 个训练、5 个验证(dev-02 整个用例留作验证)。留下的都是一次运行的前两步,最长 2036 token。

## 3. 训练结果(作业 28670)

| 项目 | 结果 |
|---|---|
| 配置 | LoRA 秩 8,alpha 16,学习率 1e-4,3 个 epoch,共 78 步,约 14 分钟 |
| 可训练参数 | 5439 万,覆盖 400 个模块(注意力、线性注意力、MLP) |
| 显存 | 峰值 9.8 / 18.6 GiB,没有任何一步 OOM |
| 速度 | 中位数每步 7.6 秒(第一步 60 秒,含内核编译) |
| 训练损失 | 第 1 个 epoch 平均 0.100,第 2 个 0.042,第 3 个 0.033 |
| 验证损失 | 0.188(训练前)→ 0.129 → 0.139 → 0.149:第 1 个 epoch 后改善,之后回升,说明过拟合 |
| 重载检查 | 800 个张量全部读回,缺失 0 个;重载前后 logits 最大差 0.0;去掉适配器后 logits 变化 10.8,证明适配器确实起作用 |

## 4. vLLM 服务与第一步对比(作业 28671)

- vLLM 0.26.0(课程公共运行时)加载了适配器,同时服务 `qwen3.8-27b` 和 `sft` 两个模型名。启动用了 255 秒。
- 对 10 个开发用例的第一步提示(与 harness 发送的格式一致,无提示;温度 0,约束 JSON 输出,关闭思考)分别提问。**10 个输出全部是合法 JSON**,适配器的输出与基座在 10 个提示上都不同。

| 看什么 | 基座 | 适配器 |
|---|---|---|
| 选对品类名(8 个有预算的用例) | **2/8** | **8/8** |
| 其中:训练过的用例 | 1/3 | 3/3 |
| 其中:验证用例(dev-02) | 0/1 | 1/1 |
| 其中:训练里没出现过的用例 | 1/4 | 4/4 |
| 缺预算时第一步就追问(2 个用例) | 1/2 | 0/2 |

基座猜的品类名有 audio、headphones、charger、phone_charger、keyboard、backpack,都不在快照里(issue #4 的现象);适配器全部用了 earbuds、chargers、keyboards、backpacks。

**缺预算的两个用例**要单独看:
- 这里我设的期望是"第一步就追问",但评分器的成功标准只看最终结果。训练数据里 dev-05 的成功运行全部是"先搜索、再追问",dev-10 是 3 次先搜索、2 次先追问。
- 所以适配器在这两个用例上先搜索,与它的训练数据一致,并不意味着它不会最终追问。第一步动作之后的行为这次没有测。

## 5. 这个试点能说明什么,不能说明什么

**能说明**:
- 整条流程是通的:轨迹 → 训练数据 → 在 INT4 检查点上训练 → peft 格式保存 → vLLM 加载服务。
- 品类名这个具体缺陷(issue #4),训练可以修掉:在没有提示的输入下,第一步选对品类从 2/8 提高到 8/8。

**不能说明**:
- **没有效果结论**。只有 10 个提示、单次采样,而且 5 个提示来自训练用例。"训练里没出现过"的 4 个用例问的仍是同样的 4 个品类,说明学会了这 4 个品类名,不说明能推广到新品类。
- **只测了第一步动作**,没有测完整运行的成功率、预算违规或回答质量。
- **训练数据很小且偏**:26 个样本,来自 5 个用例,其中 dev-01 占了 6 次运行中的大多数;训练损失降到约 0.0001,是记住而不是泛化;第 1 个 epoch 之后验证损失回升。
- **后续步骤没学到**:5K 到 10K token 的后续步骤(读搜索结果、提交方案)全被丢弃,所以工具返回之后的行为没有被训练,也没有被检验。
- **和基座对比不公平的部分**:开发集用过了(训练和检查都用它),不能再用来下结论。保留集在系统冻结前保持封存,所以正式的 SFT 对比要等 Task 6 的冻结基线。

## 6. 运行方法

```bash
# 1. 数据(轨迹来自 evaluation 分支的评测运行,用 --record-traces 采集)
python -m training.prepare_data --cases evaluations/cases.jsonl \
    --traces evaluations/results/traces-dev-28620/traces.jsonl --out data/sft/train.jsonl

# 2. 训练:先启动前确认集群上没有占 GPU 的作业
bash deploy/tacc/train-sft/stage.sh data/sft/train.jsonl
bash deploy/tacc/tools/submit-win.sh deploy/tacc/train-sft        # Windows;其他系统用 tcloud submit

# 3. 服务并对比:args.txt 里写 --adapter <集群上的适配器目录>
python scripts/make_sft_check_prompts.py --cases evaluations/cases.jsonl \
    --traces evaluations/results/traces-dev-28620/traces.jsonl --train data/sft/train.jsonl --validation dev-02
bash deploy/tacc/tools/submit-win.sh deploy/tacc/train-sft-serve
```
